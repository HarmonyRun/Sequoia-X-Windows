## 一、这个项目是做什么的

**Sequoia-X V2** 是一套 **A 股自动选股系统**（Python，8k+ star）。核心链路：

```
baostock 数据源 ──► 本地 SQLite（后复权日K）──► 7 个技术形态策略 ──► 飞书机器人推送
```

- **数据源**：baostock（免费、无需注册、无限流），彻底规避东方财富反爬
- **复权方式**：后复权（`adjustflag=1`）——历史价格不变，适合增量存储
- **存储**：本地 SQLite，可直接拷贝到别的机器用
- **推送**：飞书群机器人 Webhook，每个策略可路由到不同机器人

### 内置的 15 个策略

原项目自带的 7 个（算法未改动）：

| 策略类 | webhook_key | 选股逻辑 |
|---|---|---|
| `TurtleTradeStrategy` | `turtle` | 海龟突破：20 日新高 + 成交额过亿 + 实体阳线且真涨（防诱多），按流通市值排序 |
| `MaVolumeStrategy` | `ma_volume` | 5 日均线上穿 20 日均线（金叉）+ 当日量 > 20 日均量 1.5 倍 |
| `HighTightFlagStrategy` | `flag` | 高而窄的旗形整理突破 |
| `LimitUpShakeoutStrategy` | `shakeout` | 涨停洗盘回踩确认 |
| `UptrendLimitDownStrategy` | `limit_down` | 上升趋势中的跌停反包 |
| `RpsBreakoutStrategy` | `rps` | 欧奈尔 RPS 相对强度：120 日涨幅排名前 10% 且接近 120 日高点 |
| `PrivatePlacementStrategy` | `private_placement` | 定向增发相关形态 |

本项目新增的 8 个：

| 策略类 | webhook_key | 选股逻辑 |
|---|---|---|
| `MaBullishAlignStrategy` | `ma_bullish` | MA5>MA10>MA20>MA60 依次排列 + MA20 抬升 + 站上 MA5 |
| `MacdGoldenCrossStrategy` | `macd_cross` | DIF 上穿 DEA 且发生在零轴上方（强势区金叉）+ 放量 |
| `BollBreakoutStrategy` | `boll_breakout` | 收盘上穿布林上轨，且带宽处于近 60 日低位（挤压后突破才有效） |
| `MaGoldenCrossStrategy` | `ma_cross` | MA5 上穿 MA20 + 成交额放量 |
| `MaSqueezeBreakoutStrategy` | `ma_squeeze` | MA5/10/20/30 四线粘合（极值差<3%）后放量突破 |
| `VolumePriceRiseStrategy` | `vol_price` | 三连阳 + 成交量逐日递增 + 3 日累计涨幅 3~20% + 创 20 日新高 |
| `RsiOversoldReboundStrategy` | `rsi_rebound` | RSI(14) 超卖回升 + 收阳 + **下影线承接 ≥0.4** |
| `GapUpStrategy` | `gap_up` | 真跳空（今日最低 > 昨日最高）+ 幅度 1~9% + 放量收阳 |

外加 1 个 `custom` 容器跑用户自定义规则，所以工作台上是 **16 个可勾选项**。

> ⚠️ **RSI 策略的条件为什么不是均线**：最初写的是「收盘价仍在 MA60 上方」，
> 600 只样本实测选出 **0 只**；改成「MA20 走平」也是 0 只，再试「收盘>MA20」
> 和「MA20 今日≥昨日」全部 0 只。逐条件统计后才找到原因——
> **MA20 是 20 日均值，一只股票昨天刚跌到 RSI 30 以下时，它数学上必然还在下行**，
> 今天一根阳线来不及改变 20 天均值。所以「刚超卖」与「均线走平/向上」是互斥的，
> **任何均线类趋势过滤在这个策略里都会清零**。
> 改用当日盘面判据（下影线占比 ≥0.4）后，600 只样本从 0 只变成 10 只，
> 且这 10 只都是「昨天暴跌 3~7%、今天小幅收阳 0.4~2.6%、下影线极长」的典型形态。

### 两种运行模式

```bash
python main.py              # 日常模式：增量补数据 + 跑【已勾选的】策略 + 飞书推送
python main.py --backfill    # 回填模式：拉全市场历史 K 线（首次必须执行一次）
```

> 「跑哪些策略」可以在 Web 工作台里勾选（见 §七.5）。命令行、工作台手动触发、
> 每天 19:15 的定时任务**读的是同一份配置**，不会三处行为不一致。

- Python 用 `python-build-standalone`（npmmirror 镜像）免安装版
- Git 用 MinGit（npmmirror 镜像）免安装版
- 代码通过 `ghproxy.net` 代理 clone（已配置 git `insteadOf` 重写，见下）
- pip 走清华镜像

**git 代理配置**（已写入全局 `.gitconfig`）：

```
url.https://ghproxy.net/https://github.com/.insteadOf = https://github.com/
```

所以仓库的 `origin` 仍是官方地址 `https://github.com/sngyai/Sequoia-X.git`，
但实际拉取会自动走代理。日后 `git pull` 可直接用。若要取消：

```powershell
git config --global --unset url."https://ghproxy.net/https://github.com/".insteadOf
```

## 三、快速开始

### 1. 配置飞书 Webhook（✅ 已配置并验证）

已在 `Sequoia-X\.env` 里填好，并**实际发过测试卡片验证到达**（2026-10-12 16:04 推送成功）：

```
FEISHU_WEBHOOK_URL=https://open.feishu.cn/open-apis/bot/v2/hook/xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
```

要换成别的群，就改这一行：

```
FEISHU_WEBHOOK_URL=https://open.feishu.cn/open-apis/bot/v2/hook/你的token
```

获取方式：飞书群 → 设置 → 群机器人 → 添加机器人 → 自定义机器人 → 复制 Webhook 地址。

不填也能跑，只是推送会失败（日志里报 `飞书推送失败`），选股结果仍然会打印在日志里。
如需给不同策略配不同机器人，取消 `.env` 里 `STRATEGY_WEBHOOK_*` 的注释即可。

> 想手动验证 Webhook 通不通，跑一次日常模式即可：
> `cd "C:\Users\mjx server\Documents\股票"` 然后 `.\run-daily.cmd`

### 2. 首次回填历史数据

```powershell
cd "C:\Users\mjx server\Documents\股票"
.\run-backfill.cmd
```

当前数据源是 **auto**（东方财富 → 腾讯 → 新浪 自动探测切换，见第六节第 9 条），
2 线程并发 + 0.3 秒间隔。实测速度取决于命中哪个源：东方财富约 2 只/秒、
腾讯约 0.5 只/秒、新浪约 1.8 只/秒，全市场 5224 只大约 **20~100 分钟**。
**可中断后重跑**，已入库的自动跳过（断点续传），跑完还会自动多轮补齐缺口。

> `run-backfill-fast.cmd` 是 baostock 时代的加速脚本，现在已用不上（保留备用）。
> 想手动调并发/间隔就改 `.env` 里的 `AK_WORKERS` / `AK_DELAY`。

### 3. 日常选股

```powershell
cd "C:\Users\mjx server\Documents\股票"
.\run-daily.cmd
```

建议每个交易日 **15:00 之后**（收盘后）执行。程序会自动：
- 用交易日历确认最近一个已收盘的交易日，非交易日直接跳过
- **15:00 前运行会拒绝写入当日数据**（避免把未完成的盘中 K 线当成收盘价）
- 按每只股票**缺失的日期区间**逐只拉后复权日 K（走 `symbol_source` 里记录的源）

> ⚠️ 这里**不能**用「全市场快照」：快照给的是**不复权**的实时价，而库里的历史是
> **后复权**价，直接写进去会造出巨大的假跳空（茅台差 5 倍）。所以增量更新走的是
> 与回填完全一致的「按缺失日期拉后复权」这条路。

日志写到 `Sequoia-X\logs\daily-YYYYMMDD.log`。

## 四、每天自动运行（已配置完成）

Windows 用「任务计划程序」代替 Linux 的 crontab。**已以当前用户身份创建好**
（不需要管理员权限，创建于 2026-10-12）：

### 任务一：每日选股（19:15）

| 项目 | 值 |
|---|---|
| 任务名 | `Sequoia-X每日选股` |
| 触发 | 每周一~周五 19:15 |
| 动作 | `C:\Users\mjx server\Documents\股票\run-daily.cmd --no-pause` |
| 起始于 | `C:\Users\mjx server\Documents\股票` |
| 设置 | 错过时间后尽快补跑、电池供电也运行、超时 2 小时 |
| 验证 | 已手动触发一次，`Last Result: 0`（成功），日志 92 行 |

做的事：先把最新交易日的数据补齐，再跑 7 个策略，把结果推到飞书群；
**如果开了大模型分析**（见第七节第 7 小节），还会额外推一张 AI 分析卡片。

### 任务二：收盘后回填（16:00）

| 项目 | 值 |
|---|---|
| 任务名 | `Sequoia-X收盘后回填` |
| 触发 | 每周一~周五 **16:00**（A 股 15:00 收盘后一小时） |
| 动作 | `C:\Users\mjx server\Documents\股票\run-backfill-latest.cmd --no-pause` |
| 起始于 | `C:\Users\mjx server\Documents\股票` |
| 设置 | 错过时间后尽快补跑、超时 3 小时、不重复运行 |
| 日志 | `Sequoia-X\logs\backfill-YYYYMMDD.log` |

做的事：把全市场最新交易日的数据补上。数据源走 `.env` 的 `DATA_SOURCE`，
用 `auto` 时会在东方财富 / 腾讯 / 新浪之间**自动探测并切换**（见第六节第 9 条）。
中断了可以重跑，会自动续传。

> 为什么单独设 16:00 而不是让 19:15 一起做：这样收盘后一小时数据就位，
> 出问题时还有 3 个多小时可以重跑；19:15 那次会再校验一遍，缺什么补什么。

常用操作（把任务名换成上面任意一个即可）：

```powershell
# 查看
schtasks /query /tn "Sequoia-X收盘后回填" /v /fo LIST

# 立即手动跑一次（推荐先用这个验证）
schtasks /run /tn "Sequoia-X收盘后回填"

# 暂停 / 恢复
schtasks /change /tn "Sequoia-X收盘后回填" /disable
schtasks /change /tn "Sequoia-X收盘后回填" /enable

# 删除
schtasks /delete /tn "Sequoia-X收盘后回填" /f
```

> ⚠️ 注意：任务计划在**用户未登录时不会运行**（当前配置为「只在用户登录时运行」）。
> 如果要开机即跑，需要在「任务计划程序」图形界面里勾选「不管用户是否登录都要运行」
> 并输入账户密码。
>
> 另外：周一~周五是固定触发，遇节假日也会跑，只是当天没有新数据、策略可能选出 0 只，
> 属正常现象。

## 六、本机踩到的坑与处理

### 1. Windows 下测试有 5 个失败（上游代码问题）——**已修复**

首次 `pytest` 实测 **4 通过 / 5 失败**，原因有两类，都与本机安装方式无关：

| 失败测试 | 原因 |
|---|---|
| `test_data_engine.py::test_unique_symbol_date_constraint` | `with sqlite3.connect(...)` 在 Python 里**只管理事务、不关闭连接**；`sqlite3.Connection` 存在引用环，需 GC 才释放。测试用 `tempfile.TemporaryDirectory()`，在 Windows 上「打开的文件无法删除」，于是清理阶段报 `PermissionError [WinError 32]` |
| `test_strategy.py::test_strategy_run_returns_list_of_str` | 同上，`DataEngine._init_db()` 打开的连接没关 |
| `test_feishu.py` 3 个用例 | hypothesis 默认 `deadline=200ms`，本机跑（含 rich 日志开销）超过 200ms，报 `DeadlineExceeded`。属机器性能阈值问题 |

**已在本机修复**，提交在独立分支 `windows-compat` 上（commit `e77b4f0`）：

```
git log --oneline
e77b4f0 (HEAD -> windows-compat) fix(windows): 显式关闭 SQLite 连接 + 放宽 hypothesis 超时阈值
444c0db (master) fix(backfill): 增加重试和自动重连，解决长连接超时问题 (#91)
```

改动内容（4 个文件）：

- `sequoia_x/data/engine.py`：新增 `_connect()` 上下文管理器（保留原有「成功提交 /
  异常回滚」语义，退出时显式 `close()`），6 处连接点全部改用
- `sequoia_x/strategy/rps_breakout.py`：只读连接改用 `contextlib.closing`
- `tests/test_data_engine.py`：测试内连接显式关闭
- `tests/test_feishu.py`：3 个 hypothesis 用例加 `deadline=None`

### 2. 全市场回填比 README 说的慢很多

README 写「约 12 分钟」，那是服务器环境。本机实测：

### 3. ⚠️ baostock 会拉黑高频请求的 IP（本机已踩到）

**这是本次安装最重要的一条经验。** baostock 虽然号称「无限流」，但实测高频请求会返回：

```
login code= 10001011 msg= 黑名单用户，请与管理员联系
```

时间线（2026-10-12）：

| 时间 | 事件 |
|---|---|
| 09:06~09:14 | 正常使用，单线程/8 进程小批量均正常 |
| 09:17~09:23 | 用 8 进程、随后 16 进程连续回填全市场 |
| 09:19 | 16 进程那次：300 只里只有 14 只拿到数据，其余会话被服务端掐断 |
| 09:30 起 | 该 IP 被列入黑名单，之后所有 login 都返回 10001011 |

**结论与建议**：

- 回填请**优先用官方单线程模式**（`run-backfill.cmd`），它是项目作者设计的保守路径
- 本项目自带的 8 进程**只用于每日增量**（每只股票只有 1~2 行新数据），风险低；
  但**不要**用 8 进程去做首次全量回填（每只 600+ 行），更不要用 16 进程
- 加速脚本 `run-backfill-fast.cmd` 默认已降到 4 进程 + 0.1 秒间隔，并内置黑名单检测
  （一旦命中 10001011 立即整体停止，避免加重封禁）
- 被封后需等待服务端解封（数小时到次日不等，官方提示「请与管理员联系」）；
  已入库数据不会丢，解封后重跑会自动续传

### 4. baostock 客户端没有 socket 超时兜底

`baostock/util/socketutil.py` 的 `send_msg()` 用 `while True: recv()` 等待结束符
`<![CDATA[]]>`，服务端不响应时会**永久阻塞**。官方 `main.py` 里有一行
`socket.setdefaulttimeout(10.0)` 就是为它准备的；自己写脚本调用 baostock 时务必加上，
否则会卡死。

baostock 的当日日 K 要等收盘后（约 17:30~19:00）才发布。盘中运行时
`sync_today_bulk` 会显示「无新数据（可能非交易日）」，属正常现象。

### 6. 批处理文件必须纯 ASCII（踩坑记录）

本机 `%date%` 输出是 `周一 2026/10/12`（**星期在前**），所以 `run-daily.cmd` 里
用「取末尾 10 位」的方式解析日期：

```bat
set D=%date:~-10,4%%date:~-5,2%%date:~-2%   &rem -> 20261012
```

但更隐蔽的坑是：一开始我在注释里写了中文「周一」，结果脚本**死循环**，不断报
`'Reads' 不是内部或外部命令`、`'Logs' 不是内部或外部命令`。

命令来执行）。**所以本目录下的 `.cmd` 文件全部保持纯 ASCII**（注释也用英文），
需要中文说明就写在本文档里。

可以用这条命令自查：

```powershell
Get-ChildItem "C:\Users\mjx server\Documents\股票\*.cmd" | ForEach-Object {
  $b=[IO.File]::ReadAllBytes($_.FullName)
  "{0} 非ASCII字节={1}" -f $_.Name,(($b | Where-Object {$_ -gt 127}).Count)
}
```

### 9. 数据源升级为「多源 + 自动切换」（东方财富 / 腾讯 / 新浪）

第 7 条讲的是为绕开 baostock 封禁而切到东方财富。东方财富后来也被硬限流
（第 7 条第 2 点），所以数据源层又做了一次升级：**三个源可选，auto 模式自动切换**。

**配置**（`Sequoia-X\.env`）：

```ini
DATA_SOURCE=auto                        # auto | eastmoney | tencent | sina | baostock
AUTO_SOURCE_ORDER=eastmoney,tencent,sina
REBASE_STALE_DAYS=1
```

**auto 模式怎么工作**：

1. 启动时对每个候选源做一次健康探测（用贵州茅台拉最近 20 天）
2. 按 `AUTO_SOURCE_ORDER` 取第一个可用的源开始回填
3. 每轮结束后如果失败率超过 30%，**重新探测并切到下一个可用源**，继续补剩余数据
4. 所有源都不可用就退出（不浪费请求），下次运行自动续传

**⚠️ 最关键的一条约束：同一只股票绝不跨源拼接。**

三个源的后复权基准完全不同（实测同一只股票同一天差 40%，见第 7 条的对比表），
所以如果一只股票的历史来自 A 源、今天的数据来自 B 源，拼接处会出现假跳空。

因此程序新增了 `symbol_source` 表，记录**每只股票用的是哪个源**：

| 场景 | 处理方式 |
|---|---|
| 库里没有这只股票 | 用当前可用的源（**跨股票**用不同源是安全的） |
| 已有数据且记录了源 | **只认这个源** |
| 已有数据但没记录源（老库） | 按主源处理，可用 `migrate_source_records()` 补记 |
| 记录的源不可用，且股票已陈旧 ≥ `REBASE_STALE_DAYS` | **换源「整只重拉」**：先删该股票全部数据，再从新源拉完整历史 |

「整只重拉」会改变这只股票的历史价格基准，但**同股票内部仍然自洽**——
7 个策略用的全是同股票内部的比值（涨跌幅、量比、RPS 区间涨幅等），
所以不影响信号。这也是为什么换源只能整只换。

**为什么 `REBASE_STALE_DAYS=1`**：设为 1 表示「每日回填时，原源探测不可用、
这只股票又落后了，就立刻换源」，保证**全市场数据的截止日一致**——否则会出现
一半股票用 10-12 的数据、另一半用 10-09 的，选股结果就不可比了。
想更保守（等源挂满 2 个交易日才换）就改成 2。

**取数口径统一**（三个源都归一到项目原设计的口径）：

| 项 | 东方财富 | 腾讯 | 新浪 |
|---|---|---|---|
| 价格 | 后复权 `hfq` | 后复权 `hfq` | 后复权 `hfq` |
| 成交量 | 「手」→ **×100 换成股** | 已是「股」 | 已是「股」 |
| 成交额 | 成交额列（元） | `amount` 列（元） | `amount` 列（元） |

> 腾讯/新浪自带的 `turnover` 列是**换手率**不是成交额，代码里用成交额覆盖它。
> 否则会出现重复列，pandas 把单列当成 DataFrame，`pd.to_numeric` 直接报
> `TypeError: arg must be a list, tuple, 1-d array, or Series`（实测踩到的坑）。

**两个必须区分的语义**：`fetch_from_source` 返回 `None` 表示**请求失败**，
返回空 DataFrame 表示**请求成功但区间内没有数据**。这两者必须区分，
否则失败会被当成「这只股票没有数据」，auto 模式就永远不会切换
（这个 bug 实测踩到过，会让自动切源完全失效）。

**实测验证**（2026-10-12 17:31）：

- 三源各自取数：东方财富 ❌ 失败（硬限流中）／腾讯 ✅ 5 行／新浪 ✅ 5 行
- auto 探测结果：可用源 `['sina', 'tencent']` → 自动跳过东方财富
- 全市场回填：**5224 / 5224 只，341.2 万行，2024-01-02 ~ 2026-10-12**
  （1218 只缺口 + 4006 只原东财股票换源整只重拉）
- 最终来源分布：**新浪 4790 只 / 腾讯 434 只**（东方财富 0 只，已全部换源）
- 7 个策略全部跑通：MaVolume 92 / Turtle 123 / HighTightFlag 1 /
  LimitUpShakeout 0 / UptrendLimitDown 5 / RPS 81 / PrivatePlacement 0

**实测到的三个坑（都已修）**：

1. **失败被当成「无数据」，auto 永远不切换。** `_fetch_*` 请求失败时返回 `None`，
   但如果直接把它交给规范化函数，会得到一个**空表**，于是"失败"看起来像
   "这只股票没有数据"，探测永远通过、永不换源。现在 `fetch_from_source`
   严格区分：`None` = 请求失败，空 DataFrame = 成功但无数据。

2. **单只股票在当前源失败，不会换下一个源。** 实测 `689009` 在新浪拿不到、
   腾讯能拿到 669 行，但它就是补不上——因为原来只在「整个源不可用」时才切换。
   现在 `_plan_symbol` 返回**候选源列表**，逐只按顺序试，第一个成功的源就用它。
   只有「全新股票」和「整只重拉」才给多个候选源；已有数据的股票仍然只给一个源，
   避免同股跨源拼接。

3. **数据写进去了、来源没记上 → 同股跨源拼接。** 原来先写数据后记来源，
   进程在两步之间被杀就会留下「有数据但没来源记录」的股票，下次增量按主源去拉，
   而数据其实来自另一个源。现在 `_store` 在同一个事务里**先记来源、再写数据**，
   最坏情况变成「有来源没数据」，那只股票会被当成全新股票重新拉，不污染已有数据。

**12 只「没跟上最新交易日」的股票是正常现象**：`002731`、`000016`、`688496` 等
最后交易日停在 8~9 月，实测从新浪和腾讯都拿不到之后的任何数据——它们是**停牌股**。
每次回填都会重新检查它们（12 次请求，很便宜），复牌后自动跟上。

**速度实测**（拉 2024-01-01 起全历史，2~3 线程）：

| 数据源 | 单只耗时 | 全市场 5224 只估算 |
|---|---|---|
| 新浪 | 0.56 秒 | 约 25 分钟 |
| 腾讯 | 1.85 秒 | 约 98 分钟 |
| 东方财富 | 约 0.5 秒 | 约 40 分钟（但连拉几千只会被硬限流） |

### 10. 批量选股性能：全市场缓存（246s → 67s）

**问题**：16 个策略各自遍历一遍全市场，每只都调一次 `engine.get_ohlcv()` ——
合计 **8.4 万次 SQL 查询**。而所有策略用的是**同一份数据**，
等于把同样的 341 万行重复读了 16 遍。

**实测**（15 个策略，排除要发网络请求的定增监控）：

| | 耗时 | 查库次数 |
|---|---|---|
| 关缓存 | 246.3s | 67,868 次 |
| **开缓存** | **67.2s** | 79 次 |

**做法**：新增 `sequoia_x/data/ohlcv_cache.py`，一次性把全市场读进内存、
按 symbol 分组，`get_ohlcv` 先查缓存、未命中才查库。
**17 个调用点一行都没改** —— 策略代码完全不知道缓存的存在。

`pipeline.run_strategies` 开跑前 `warm_cache()`，`finally` 里 `release_cache()`。

#### 内存是怎么从 1475MB 压到 619MB 的

`pd.read_sql` 读 341 万行时，**pandas 只占 111MB，但 RSS 峰值 1475MB** ——
差的 1.3GB 全在它内部的中间过程（一次性把 341 万行 fetch 成 Python 元组）。
改成 `fetchmany(20万)` 分批 + 直接写进预分配的 numpy 数组后，峰值降到 341MB。

#### ⚠️ 最重要的一条：float32 会让选股结果不一致

一开始为了省内存用 float32，实测发现：

```
ma_cross（MA5 上穿 MA20）：关缓存 810 只 / 开缓存 813 只  ← 不一致
```

原因：float32 只有约 7 位有效数字，而后复权价能到 5 位数（茅台 11000+）。
当 MA5 与 MA20 的差值小于 float32 精度时，
`prev_ma5 <= prev_ma20 and now_ma5 > now_ma20` 这个判断会翻转。

**同一份数据开不开缓存给出不同信号，对交易工具是不可接受的**，
所以改回 float64。代价是峰值从 341MB 涨到 619MB —— 这笔账值得。

#### 内存安全性（工作台是常驻进程，必须验证）

反复 warm/release 4 次：

```
基线 76MB → warm 后 695MB（+619）→ release 后 87MB
第 2/3/4 次 warm 峰值都是 695MB，不再增长
```

**不累积**，`release()` 后回到 ~90MB。内存紧张可设 `CACHE_MARKET_DATA=false`
退回逐股查库，**选股结果完全一样，只是慢**。

#### 缓存失效

用「行数 + 最大日期」当指纹，回填或增量同步后自动失效，不会读到旧数据。
（比文件 mtime 可靠：SQLite 在 WAL 模式下主库 mtime 不随提交更新。）

#### 踩过的两个坑

**一、验证优化效果时，对照表必须真的没走优化路径。**
我一度用「开缓存 vs 关缓存比总耗时」验证，得到「只快 6.8s」的错误结论 ——
因为 `run_strategies` 已经内置了 warm_cache，**两组对比都走了缓存**，
比的是同一件事。后来改用探针统计 `get_ohlcv` 的真实查库次数才发现真相。

**二、`.gitignore` 里不带前导斜杠的 `data/` 会匹配任意深度。**
这条本意是忽略根目录数据库的规则，把 `sequoia_x/data/` 也匹配掉了，
于是新增的 `ohlcv_cache.py` **被静默排除在提交之外**。
而 `engine.py` 因为规则生效前就已被跟踪反而没事。

这种 bug 的隐蔽之处在于**它只对新文件生效**：
本地一切正常、`git status` 干净，只有远端少了文件。
现在全部路径规则都锚定到仓库根（`/data/`），并加了暂存区安全检查。

### 3. 「核查停牌」是干什么的——以及为什么需要它

库里**永远会有十几只股票的「最新日期」落后于大盘**。这有两种可能，光看数据库分不出来：

- 这只股票**停牌**了（数据没问题）
- 我们的数据源**漏了**它的数据（数据有问题，要回填）

所以工作台提供了一个核查按钮：拿这些股票的代码去问**新浪实时行情**，看两个字段——

| 字段 | 正常交易 | 停牌 |
|---|---|---|
| 状态码（第 33 个字段） | `00` | `03` |
| 成交量 | 几十万~几亿 | `0` |

**实测（2026-10-12）**：

```
贵州茅台  状态码 00  成交量 3,155,604      ← 正常交易
平安银行  状态码 00  成交量 105,863,456    ← 正常交易
宁德时代  状态码 00  成交量 41,706,382     ← 正常交易
信达证券  状态码 03  成交量 0              ← 停牌
*ST康佳A  状态码 03  成交量 0              ← 停牌
```

对当时那 12 只「落后」股票核查的结果：**12 只全部是停牌（状态码 03、成交量 0），0 只漏数据**。
换句话说，`核查 12 只：停牌 12 只（数据没问题）` 就是数据完整的证明。

> 停牌股每次回填都会被重新检查（12 次请求，很便宜），复牌后自动跟上。

| 设置项 | 默认值 | 说明 |
|---|---|---|
| 数据源 | `auto` | auto / eastmoney / tencent / sina / baostock |
| auto 尝试顺序 | `eastmoney,sina,tencent` | 逗号分隔；某个源挂了自动换下一个 |
| 回填并发线程数 | `3` | **调到 4 以上有风险**，见第六节第 9 条的实测数据 |

**数据操作**（4 个按钮，都在后台跑，进度去「运行与日志」页看）

| 操作 | 做什么 | 什么时候用 |
|---|---|---|
| 回填当日最新数据 | 只补最新交易日的缺口，已是最新的直接跳过 | 收盘后想立刻看结果 |
| 补齐全市场缺口 | 全市场扫描，自动跳过已是最新的，自动换源续填 | 常规补齐 |

> 万一所有数据源都失败，原数据一行都不会丢。工作台上点它会有二次确认。
>
> 「指定日期区间」还有一个保护：同一只股票只允许用它记录里的那个数据源。
> 如果那个源当前不可用，这只股票会被**跳过**而不是换个源补一段——跨源拼出来的
> 历史会有假跳空，宁可这次不补。

（「立即运行」会真的跑一遍并推送到飞书，所以也有二次确认；工作台里有任务在跑时会拒绝，
避免两个进程同时写数据库。）

**数据库与缓存**
- **「备份数据库」**：用 SQLite 的在线备份接口，**有别的进程正在写也能拿到一致的快照**，
  存到 `data\backups\`，只保留最近 5 个（491MB 的库别让它无限堆）
- **「清理缓存」**：可以单独或一起清掉信号缓存 / 任务历史 / 股票名称表 / 数据覆盖缓存
  （「选股结果页一直不刷新」的时候用它）

#### 两个实现上的注意点

**一、改完 `.env` 怎么让它立刻生效。** `get_settings()` 是**进程级单例**，而且
`DataEngine` 会把当时的 settings 存一份在自己身上。所以保存配置后必须做三件事，
少一件就会出现「改了没生效」：重置 Settings 单例 → 丢掉缓存的 DataEngine →
清掉依赖配置的数据缓存（数据覆盖、库统计、任务状态）。

**二、写 `.env` 必须保住原文件。** 那个文件里有大量解释性注释（为什么用某个数据源、
踩过什么坑），是给人看的文档，不能因为改一个值就被冲掉。所以是按行处理：
注释、空行、顺序全部保留，只替换目标键；被注释掉的键（比如
`# STRATEGY_WEBHOOK_RPS=...`）**就地取消注释**，而不是在文件末尾再追加一行。
写完立刻回读校验，任何一个键对不上就用 `.env.bak` 还原并报错——
**改配置改坏了比不改更糟**。

### 6. 用自然语言创建选股策略（需要先配大模型）

在「选股策略」面板下方的**自定义策略**区：

1. 输入框用中文描述，例如「找连续三天缩量回调、今天放量收阳的票」
   （旁边有 4 个示例标签，点一下直接填入）
2. 点「**生成规则**」，等 30~90 秒
3. **预览确认**：显示策略名、试跑命中多少只、命中样例、完整规则 JSON
4. 确认后点「保存这个策略」
5. ⚠️ **回到上面勾选「自定义策略」并保存设置**，它才会参与选股

#### 为什么不让大模型直接写 Python 代码

生成的代码能读写文件、发网络请求、改数据库；引用一个不存在的列名就能让整条
流水线挂掉；而且用户看不懂、也改不动。

改成**受限规则 JSON** 之后：
- 指标名、操作符、参数范围都在白名单里，本地能校验
- 规则是给人看懂的格式（「MA5 上穿 MA20 且 成交量 > 20日均量×1.5」）
- 生成的结果用户能直接改数字，不必重新问大模型

格式定义见 [`docs/自定义策略DSL.md`](自定义策略DSL.md)。

#### 大模型的输出不可信，所以有校验 + 重试

实测大模型常犯这些错，全部由本地校验拦住：

| 模型的错误 | 本地怎么处理 |
|---|---|
| 编造指标名（`avg_price`、`turnover_rate`） | 白名单校验失败 → 把错误回灌让它改 |
| 把 `{"ind":"const","value":1.5}` 写成 `{"const":1.5}` | 报错时直接给出正确写法提示 |
| 该用 `cross_above` 的地方用 `>`（语义完全不同） | 能通过校验，但试跑结果会暴露问题 |
| `period` 写成 500（超出 250 上限） | 校验层拦下（不是等运行期才报错） |

流程是「生成 → 本地校验 → 失败则把错误信息喂回去让它自己改」，**最多 3 次**。
校验通过后还会**抽样试跑 120 只股票**，把「大概能选出多少只」告诉你——
有些规则语法正确但实际算出全是 NaN，不试跑用户不会知道。

预览里如果命中率是 0，会提示「条件可能过严」；超过 30% 会提示「条件可能偏松」。

#### 生成一次要多久

30~90 秒，因为要跑两步：大模型翻译（通常 10~40 秒）+ 抽样试跑 120 只股票。
生成期间按钮会禁用并显示「生成中…」，是正常的，不要以为卡死了。

#### 自定义策略怎么参与选股和推送

它作为一个 `custom` 容器接进标准流水线，跑的时候**一次遍历全市场、
对所有自定义规则同时判定**（而不是每条规则各遍历一遍，那样规则多了会非常慢）。

**推送时按规则分开推**：建了 5 条规则就会收到 5 张卡片，
不会混成一张让你分不清哪只票是谁选的。

坏规则只跳过它自己——某条规则非法，不影响其它自定义规则，更不影响 15 个内置策略。

### 7. 大模型分析（可选）

开启后，**每次跑完选股**（命令行 `main.py`、工作台点「运行日常选股」、以及每天 19:15 的
自动任务）会多做一件事：把当天的市场和信号交给大模型分析，分析结果作为**一张单独的卡片**
推送到飞书。

#### 怎么配

工作台 → 设置 → **大模型分析（可选）**：

| 设置项 | 说明 |
|---|---|
| 启用大模型分析 | 关闭 / 开启 |
| 接口地址（Base URL） | 填到 `/v1` 为止即可，程序会自动补 `/chat/completions` |
| 模型名 | 必须和服务商文档里的名字完全一致 |
| API Key | 本地 Ollama 不需要鉴权，留空即可 |

卡片右上角有「**测试大模型**」按钮——**这是最该先点的**：地址或模型名写错**不会在选股时报错**，
只会静默分析不出来。点一下会真的调一次，几秒钟就知道通不通；而且不用先保存，
可以直接拿输入框里的值测。

用的是 **OpenAI 兼容的 `/chat/completions` 接口**，所以同一套配置能接：

| 服务 | Base URL 示例 | 模型名示例 |
|---|---|---|
| DeepSeek | `https://api.deepseek.com/v1` | `deepseek-chat` |
| 通义千问 | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-plus` |
| 智谱 | `https://open.bigmodel.cn/api/paas/v4` | `glm-4-plus` |
| OpenAI | `https://api.openai.com/v1` | `gpt-4o-mini` |
| 本地 Ollama | `http://localhost:11434/v1` | `ollama list` 里那个名字 |

#### 它到底分析什么

不是把几个股票代码丢给模型空谈，而是**先把当天的市场事实算好**（这些数字直接来自本地数据库）：

- 交易日、全市场只数
- 上涨 / 下跌 / 平盘家数
- 涨停（≥9.8%）/ 跌停（≤-9.8%）家数 ← 近似值，ST 股其实是 ±5%
- 平均涨跌幅、总成交额（亿元）

然后附上 7 个策略各自选出的股票（**带中文名**）。实测发给模型的内容长这样：

```
交易日：2026-10-12
全市场：5210 只，上涨 1099 家、下跌 4031 家、平盘 80 家
涨停（≥9.8%）55 家、跌停（≤-9.8%）37 家，平均涨跌幅 -1.59%，总成交额 15368.4 亿元

各策略选股结果：
- 均线放量（92 只）：000156 华数传媒、000420 吉林化纤、…
- 海龟交易（123 只）：000429 粤高速A、000498 山东路桥、…
- 高旗形整理（1 只）：603151 邦基科技
- 涨停洗盘：无信号
```

要求模型输出三段：**市场概况 → 策略信号解读 → 关注方向与风险**，500 字以内，
并且**明确要求不得给出买卖建议**。

#### 几个实现上的取舍

- **每个策略最多列 25 只**给模型。海龟交易一次能选出 123 只，全塞进去既贵又没用——
  模型看的是「方向」不是「清单」，超出部分只报个总数。
- **模型输出的 `#` 标题会被降级成加粗**。飞书卡片用的 `lark_md` 不支持标题语法，
  不处理的话会原样显示成「# 市场概况」。
- **没配就安静跳过**，任何失败都只记日志。分析是附加价值，不能因为大模型挂了
  就让选股结果推不出去。
- 分析结果**只推送、不写回数据库**，避免污染信号数据。

### 8. 工作台是怎么实现的（为什么没有引入任何新依赖）

用**纯 Python 标准库**（`http.server.ThreadingHTTPServer`）写的，前端是**原生 HTML/CSS/JS**，
图表（环形图、柱状图、K 线图）全部手写 SVG。

这么做是因为：这台机器装依赖要走代理，而工作台只是本机自用，标准库完全够用；
更重要的是**不动 `pyproject.toml` 的依赖清单**，`uv sync` / `pip install` 不会因此有任何变化，
也不会出现「工作台跑不起来是因为某个前端库没装」这种问题。整个页面离线可用，不引用任何 CDN。

新增的文件（都在 `webui/` 目录下，与原有代码隔离）：

```
Sequoia-X\webui\
├── __init__.py
├── server.py            # HTTP 服务 + JSON 接口 + 后台任务
├── envstore.py          # .env 的安全读写 + 设置项描述与校验
└── static\
    ├── index.html       # 六个页面的骨架
    ├── style.css        # 深色主题
    └── app.js           # 全部交互与手写 SVG 图表
```

同时新增了 `sequoia_x\pipeline.py`，把「跑 7 个策略」这段流程抽出来给命令行和工作台共用——
**策略列表只在 `STRATEGY_CLASSES` 维护一处**，以后加策略两边都会自动带上，不会漂移。

### 10. 注意事项

- **「运行日常选股」会真的往飞书群推送**。只想看信号就用「只计算信号」。
- 工作台读的是 `data\sequoia_v2.db`，和命令行、计划任务用的是同一个库，数据实时一致。
- 股票名称表第一次会在线拉一次（akshare），之后缓存在 `data\name_cache.json`，7 天内不再联网。
- 信号计算结果缓存在 `data\signals_cache.json`，重启工作台不会丢。
- 后台任务历史持久化在 `data\jobs_history.json`（保留最近 50 条，每条带最后 200 行日志），
  重启工作台后「历史任务」还在；如果上次是直接关掉工作台的，那个任务会标成「已中断」。
- 页面默认深色主题，适配 1280px 以上宽度；窄屏卡片会自动换行，表格横向滚动。

## 八、Windows 安装包（分发给别人用）

前面十节讲的都是**本机**这套已经装好的环境。如果你要把 Sequoia-X 给别人用——
对方不想碰命令行、不想装 Python、不想配依赖——就用安装包。

### 1. 怎么用

把 `Sequoia-X-Setup.exe`（**约 80 MB**）发给对方，对方双击即可：

1. 选安装位置（默认 `%LOCALAPPDATA%\Programs\Sequoia-X`，**不需要管理员权限**）
2. 点「安装」，等十几秒
3. 装完勾「立即启动」，浏览器会自动打开工作台

之后桌面上会有「Sequoia-X 工作台」图标，双击就启动；开始菜单里有「卸载 Sequoia-X」。
**第一次启动工作台时，程序会自动登记两个计划任务**（每个交易日 16:00 回填、19:15 选股），
在「设置 → 计划任务」里能看到和管理。

对方第一次要做两件事：

1. **回填历史数据**——安装包里**不含**任何行情数据，装完是个空库（总共 5224 只股票）。
   去 **设置 → 数据操作 → 「补齐全市场缺口」**，大约 1.5 小时（可以关掉浏览器，后台会继续跑；
   也可以在「运行与日志」页看进度）。**不回填就没有任何选股结果。**
2. **填飞书 Webhook**（可选）——去「设置 → 飞书推送」填自己的 Webhook。
   不填也能用，只是不推送，选股结果在工作台里看。

> 如果希望对方装上就能直接用（省掉那 1.5 小时），打包时加 `-WithData` 参数，
> 安装包会变成约 204 MB，里面带一份打包当天的全市场后复权日线。

### 2. 安装包里有什么

### 3. 怎么自己打这个包

**不需要 Inno Setup / NSIS / 7-Zip / PyInstaller**——用 Windows 自带的
`.NET Framework` 编译器 `csc.exe` 编译 C# 安装器，配一个便携 Python 运行时：

```powershell
cd "C:\Users\mjx server\Documents\股票"
.\build\build-installer.ps1                 # 默认：不含行情数据（约 80 MB）
.\build\build-installer.ps1 -WithData       # 带上行情数据（约 204 MB）
.\build\build-installer.ps1 -SkipAssemble   # 负载已就绪，只重新编译打包
```

产物：`installer\dist\Sequoia-X-Setup.exe`

| 文件 | 作用 |
|---|---|
| `build\assemble-payload.ps1` | 铺负载目录（便携 Python 裁剪 + 依赖 + 应用 + 配置 + 数据） |
| `build\make-payload-zip.py` | 压缩成 payload.zip（deflate 9；**不能用 LZMA**，.NET 的 ZipArchive 不认） |
| `build\build-installer.ps1` | 一键串起：组装 → 编译 C# → 压缩 → 追加负载 |
| `installer\Setup.cs` | 安装器（GUI + `/S` 静默模式） |
| `installer\Launcher.cs` | 启动器（起服务、开浏览器、可停服务） |
| `installer\Uninstaller.cs` | 卸载器 |
| `installer\build.ps1` | 用 csc.exe 编译三个 exe，并把 zip 追加到安装器末尾 |
| `installer\verify-payload.ps1` | 30 项自动验证（zip 定位、前缀过滤、解压一致性…） |

### 4. 静默安装（给自动化用）

```powershell
Sequoia-X-Setup.exe /S /D="D:\Apps\Sequoia-X" [/NoData] [/NoDesktop] [/NoStartMenu] [/AutoStart] [/Launch]
Uninstaller.exe    /S [/KeepData]
```

退出码：`0` 成功 / `1` 通用错误（写 `install-error.log`）/ `2` 参数错误 / `3` 负载缺失 / `4` 目标目录不可写。

> ⚠️ 这三个是 **GUI 子系统**程序，PowerShell 里 `&` 调它们**不等待**，
> `$LASTEXITCODE` 是上一次命令的旧值。要么加 `| Out-Null`，要么用
> `Start-Process -Wait -PassThru` 取 `.ExitCode`。

### 5. 打包时踩到的坑（都修了）

1. **追加 zip 的起点算错**。zip 数据追加在 exe 末尾，定位时不能把 EOCD 的位置当成
   zip 起点——正确公式是 `zip起点 = EOCD位置 - 中央目录大小 - 中央目录偏移`。
   算错的话读出来的偏移越过文件末尾，安装器会报「安装包不完整」。
2. **`ZipArchive` 不能直接吃整个 exe**。.NET Framework 会把中央目录里「相对 zip 起点」
   的偏移当成「相对流起点」，直接抛 `InvalidDataException`。必须喂给它一个**起点就是
   zip 第一字节**的流。
3. **中文 `.cs` / `.ps1` 必须存成 UTF-8 带 BOM**。Windows PowerShell 5.1 读无 BOM 的
   `.ps1` 会按 GBK 解析（直接语法报错），.NET Framework 的 csc 读无 BOM 的 `.cs` 会按
   GBK 读字符串（编译出来的界面全是乱码）。
4. **服务器启动不能卡在联网上**。原来 `main()` 在开始监听**之前**同步拉取股票名称表，
   而这台机器上它走的 `82.push2.eastmoney.com` 被墙，结果端口 25 秒都没监听、启动器
   超时报失败。改成**先监听、预热丢后台线程**，装完 4~16 秒就能打开页面。
5. **计划任务必须用 XML 建，不能用 `schtasks /tr`**。只有 XML 能指定 `<WorkingDirectory>`，
   否则任务在 `system32` 下启动，应用按相对路径找不到 `data\sequoia_v2.db`，会新建一个空库。
6. **`New-Item`/`FolderBrowser` 选择的目录里如果同名文件存在**，安装器要给出明确的
   「目标目录不可写」而不是解压到一半失败——退出码 `4` 覆盖了这个情况。

### 6. 分发给别人之前请注意

- 安装包**没有数字签名**，部分杀毒软件会拦截，让对方把安装目录加白名单
- **默认包里不含行情数据**，对方装完必须自己回填一次（约 1.5 小时），
  否则是个空库、选不出任何股票。想省掉这一步就用 `-WithData` 打带数据的包
- 内置的行情库是**后复权**数据，换数据源会导致价格基准变化（见第六节第 9 条）
- 卸载默认**保留** `app\data` 和 `app\.env`（防手滑丢数据），要连数据一起删得在
  卸载界面勾选，或者静默卸载时不加 `/KeepData`
- 大模型分析默认关闭；对方要自己填 API Key。**API Key 会以明文存在 `app\.env` 里**，
  提醒对方别把那个文件连同安装目录一起发出去
